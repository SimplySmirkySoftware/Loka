# Project rules

Use [DESIGN.md](DESIGN.md) as the routing map for design information. Follow
only the documents relevant to the question at hand; exact API and behavior
facts remain authoritative in headers and discriminating tests.

For proposal and design judgment, also follow [PHILOSOPHY.md](PHILOSOPHY.md).
When choosing between plausible implementations, prefer the option that best
matches Loka's philosophy of meaningful app-facing code, explicit ownership,
clear boundaries, and small reusable concepts.

This file states rules. Values that change as work lands, such as counts,
approvals, revisions and coverage status, stay in their own record (a rig
descriptor, a design document, the code) and are linked from here, not copied.

## Core Constraints
- Loka repository code should remain compatible with the project's target platform constraints; treat C++98 as the baseline unless a narrower file- or platform-specific rule explicitly allows otherwise.
- The C++98 baseline binds code that ships, not tooling that only inspects it. For static checking, reach for the newest compiler and tools available and use them aggressively: extra `-W` probes over `compile_commands.json`, modern-only diagnostics the Retro68 toolchain cannot produce (`cmake/LokaWarnings.cmake` already records `-Wmismatched-new-delete` as one), sanitizers, static analyzers, `clang-tidy`, `clang-format`, and `static_assert` behind a C++11+ gate. A check that finds a real defect is worth running even if no supported target could ever run it. Three limits keep this free: the check must not become a prerequisite for building or running Loka on any target, it must not change what ships, and its invocation and result belong in the PR so the next person can repeat it rather than rediscover it.
- Prefer compile-time errors over runtime checks; leverage templates, inheritance constraints, and SFINAE to catch misuse at build time.
- Use TypeTag static checks automatically when the compiler supports `static_assert` (C++11+). In C++98 builds, keep optional TypeTag checks behind explicit `LOKA_*_CHECK_TYPETAG` gates so classic/release builds stay lightweight.
- C++ exceptions are disabled; do not add `try`/`catch` or rely on throwing.
- Loka applications are single-threaded at the application layer; all UI and DSL logic must execute on the Main Thread. Multi-threading and concurrency are deferred to OS/platform-specific implementations, which must dispatch results back to the Main Thread.
- Prefer explicit error handling and nothrow/nullable patterns in Classic builds.
- Use `assert` for contract violations (e.g., null PlatformContext); do not throw.
- Secrets/PII must not be hardcoded; use env vars and avoid logging sensitive data.
- Use English for code comments, code-facing docs, and API/design notes that ship with the repository; keep non-English prose for user conversation only unless a file already has an established localized convention.

## Ownership And State
- A window set that follows a list is a `DocumentRoster<T, N>` (framework-owned list and tracker) declared once in the App composition; the App's seat adds the windows of new documents and then closes the windows of documents removed with `close`, in that order within one admission, and a document whose window is refused is dropped, never retried. [Document-driven window set](docs/KeyedSeatDesign.md#document-driven-window-set)
- List changes are data-side facts: `ObservableList<T>` in `common/core` has no view dependency and publishes one `State<ListRevision>` carrying `structure`, `content`, and `change`; the view consumes that publication and never infers a diff. [List identity and working copies](docs/ObservableListDesign.md#from-agentsmd)
- Generation-scoped state belongs in a box with that specific role, not a nested Boundary: `LazyScope` is a Keyed-shaped seat whose runtime root owns the arm's states and declares the arm. [LazyScope storage](docs/KeyedSeatDesign.md#lazyscope)
- States created inside a Keyed/LazyScope runtime generation use the tagged heap state gate; a Section stays their logical owner; Boundary-lifetime states and Sections outside such generations keep the StateArena. [Generation state ownership](docs/KeyedSeatDesign.md#keyed-declaration-seats)
- Bindings are declared in `declareBindings(BindingToken&)`, which `ComposableNode` calls when opening a declaring window, including attach; `Node::bindingsFollowProps()` also refreshes bindings on retained props application. A Keyed declaration does not reopen its enclosing boundary's binding window; newly materialized descendants open their own attach windows. The token is the only door; immediate watches run synchronously inside that call, before `composeNode` reads any state they write. The node-owned token is armed only during that call; disarmed use asserts in lifecycle-audit builds and refuses without binding otherwise. `attachNode` remains for attach-scoped resource work, gated by the resource's own presence; initial values and one-time computations belong in state declarations or constructors.
- Keep scopes small by default. Prefer immutable completed values, explicit owners for mutation, and small encapsulated types when a feature needs multiple pieces of internal state.
- Before adding new variables, especially member fields, consider whether they introduce long-term ownership/lifecycle/cleanup complexity. Prefer reusing an existing owner or encapsulating the state so management does not become more fragmented over time.
- When state or variables must be introduced, consider whether they should be encapsulated or expressed as a small state machine instead of scattered flags. Prefer lifecycle-aware structures that make ownership, transitions, and cleanup easier to reason about.
- Prefer immutable value objects for facts, snapshots, props, plans, and completed analysis results. Use builders, local temporaries, or explicit owner state for construction/mutation, then expose the completed value through a read-only API. If this choice is ambiguous before implementation, stop and confirm whether the feature should prioritize immutable structure or measured mutation/reuse.
- Separate facts from operations. A growing set of mutable properties plus general-purpose methods usually means a class is becoming an accidental owner/controller. Prefer small value objects, stack-local diff/result construction, Flow/action/policy objects, repositories, or platform seams over turning any long-lived framework object into a broad controller.
- Performance-sensitive mutation is allowed when 68030-era or other supported target constraints make copying too costly, but the mutable phase, owner, and cleanup path must remain explicit. Prefer splitting immutable sections into separate value types over making a broad object mutable.
- A `MutableState<T>` registered on a StateTracker is written only inside that tracker's transaction (RAII guard); a State registered on no tracker notifies synchronously and needs no bracket (`Scene::attached_`, `SceneManager::currentScene_`).
- Ownership policy: follow gravity. Parent owns child-facing state/data by default; cross-boundary sharing must be explicit and should use a meaningful owner/facade. `Managed<T>` is internal value plumbing, not the app-facing ownership model. Broad reuse should prefer global caches for immutable/shared resources. Avoid designs where a child effectively owns or stabilizes its parent.
- Held policy: use `Held<T>` for passive payloads whose lifetime should follow explicit Boundary/Section scopes. Handle copies are inert views and do not retain; `Held<T>` governs lifetime, not payload mutation authority. Acquire a lifetime edge through `hold()` in the nearest owner, keep holds inside the creator subtree, never use a copied view past the holding scope/creator landlord, and treat nullable refusal as part of the API. Detach drops owner slots synchronously, the last drop queues the releaser on the Boundary clock, and block storage remains with its arena landlord until reclaim. Diagnose the owner ledger (`held-by [...]`), not an alias count.
- Boundary access policy: `currentBoundary()` is the owner-side path; `findBoundary()` is for direct-parent borrowed access only. Do not rely on multi-hop or sibling boundary traversal from DSL code.
- State creation policy: create ordinary Node/Boundary-owned mutable state through lifecycle-aware APIs such as `state()` and `declareStates()`. Ad hoc state creation helpers such as `dangerouslyUseState()`, and every `dangerously*` state access or creation, are escape hatches: keep their callsites out of normal `common/` and `example/` DSL code unless there is a documented reason, and treat a new usage as a design event that requires explicit review, not routine implementation. [Dangerous APIs](docs/ProgrammingGuide.en.md#7-dangerous-apis-are-escape-hatches)
- NodeState storage policy: a component may keep `NodeState<T>` members only for its own Node/Boundary-owned state declared through lifecycle-aware state APIs such as `state()` or `declareStates()`. Do not expose `NodeState<T>` across boundary lines or use it as a foreign mutation channel. The one sanctioned exception is the rail result channel: a Props door that borrows the app's `NodeState<T>` so the platform rail can write a fact into it (`OpenFileDialogProps::result`, `ScrollViewProps::offset`, `RectSurfaceProps::laidOutExtent`); the node writes only through `NodeState::set` and reads the handle only for props identity. A fact the rail reports and a request the app posts are two separate boxes with one kind of writer each; see [Request delivery](docs/RequestDeliveryDesign.md#from-agentsmd).
- Request delivery policy: a rail delivers pending requests only at the completion of an entry operation, never from a shared helper, and each delivery is bounded; the site inventory and the bound live in [Request delivery](docs/RequestDeliveryDesign.md#from-agentsmd).
- Input-operation policy: rail native-input entries must route all work in their controller borrow interval through the rail input door, whose unconditional `BorrowScope` (formerly `OperationScope`) restores without pumping; see [Input-operation door](docs/RequestDeliveryDesign.md#input-operation-door-977) for current coverage and owner/native exceptions.
- Request queue policy (#892, PR #893): a request type whose effect accumulates (a command) is declared as `RequestQueue<T, N>`, never `Request<T>`; the trait wall refuses it at declaration. Queues are app-owned endpoints and rails never see the ring. [Endpoint and queue](docs/RequestDeliveryDesign.md#endpoint-and-queue-892).
- Focus policy (#911, #960): keyboard focus is reported into the fact box of an app-owned `Focus<K>` (one per screen by convention, declared in the same Scene as the fields that borrow it), whose second box carries the app-posted request; each Scene's `SceneFocus` owns its single publication and takes at most one request per completion; rails call `App::reconcileFocus` at their outer completion, answer `readNativeFocus` and `applyNativeFocus`, never write the fact from native notifications, and keep no duplicate publication record. [Focus design](docs/FocusDesign.md#from-agentsmd)
- NodeState pass-through policy: when a DSL/API needs read-only live state, pass `nodeState.state()` explicitly instead of relying on implicit conversions from `NodeState<T>`. [NodeState](docs/ProgrammingGuide.en.md#nodestatet)
- NodeState internal-surface policy: owner/tracker access on `NodeState<T>` is internal and should stay behind `dangerously*` naming; ordinary DSL code should use `get()`, `set()`, and `.state()` only. [NodeState](docs/ProgrammingGuide.en.md#nodestatet)
- Flow ownership policy: long-lived Flow/StateStream chains owned by a Node or Boundary should be stored in `FlowSlot<T>` or an equivalent lifecycle-aware slot. Keep one-shot stack Flow usage limited to tests or bounded local operations.
- Flow state policy: do not share mutable state between unrelated Flow instances just because a value must change. Prefer Flow-owned input/result state, dedicated result state, or read-only input state. When multiple inputs should drive one event/result, consider `DerivedState`, an emitter adapter, or an explicit owner facade rather than passing the same `MutableState<T>*` through several Flow paths.
- Ownership/binding policy: distinguish borrowed live state from props-owned constant values explicitly, and let the logical node layer decide which states are live. Props-owned constant values may reuse internal storage helpers, but they must not be registered as observed state or bound/unbound through `NativeNodeContext` live-state paths. `PlatformController`/`NativeNodeContext` code binds only states the logical layer has classified as live, re-decides liveness only as a defensive guard, and guards against null/empty state before drawing or binding. [Props and definitions](docs/ProgrammingGuide.en.md#props-and-definitions)
- Retirement policy (two lines, see PHILOSOPHY "Lifetime Has Two Lines"): detach work (unbind, back-pointer deregistration, cancelling pending work, stripping or queueing native handles) is synchronous and happens on the detach path; memory reclamation is deferred to the owning clock's boundary and must fire nothing observable (no callbacks, no state writes in destructors of deferred-reclaimed objects). Do not `delete` chain residents synchronously inside rebuild/apply passes; retire them into the owner's pool. Shared native-resource tickets follow the PlatformContext clock and quiescent shutdown contract in [Native resource retirement](docs/NativeResourceRetirementDesign.md).
- Failure-atomicity policy (see PHILOSOPHY "Failure Is An Input"): structural replacement must clone/build into temporaries (`OwnedDef<T>`) and commit only on full success; never destroy the old value before its replacement exists. Anything consumed before a fallible commit (dirty flags, one-shot tokens, queued events) must be requeued/restored on failure or consumed only at the commit point. Blob producers follow the [refusing storage and seal protocol](docs/BlobStorageDesign.md).
- Failure-degradation direction: preserve-old applies to live truth (the value the app is showing or acting on, e.g. the installed menu bar); derived/applied-state caches degrade the opposite way — clear on failed capture so the next pass full-rebuilds, because a stale reconciliation baseline is more dangerous than an empty one.
- Definition ownership policy: hold owned Definition clones in `OwnedDef<T>`; `clone()` may return 0 (OOM only) and every call site must handle it. Do not use `OwnedDef<T>` for runtime chain residents (Scene/Node/Boundary instances) — their lifetime belongs to owners and clocks, not wrappers.
- Scheduler retry policy: before scheduling work from inside a scheduler callback, check the scheduler's drain-loop semantics (`NextTickTracker::run` drains repeated requests within one flush, bounded by `maxIterations_`). Schedule failure retries after the current run completes so a persistent failure costs one attempt per run/flush, not a spin (the tracker has no tick identity; a second flush in the same event-loop turn may retry again).

## Design Taste
- Prefer designs that make ownership, lifecycle, and update flow visible in the type or API shape.
- Prefer code that can be reviewed safely by shape. During detailed design, treat it as a high-priority concern that safety, relationships between objects, ownership, lifecycle, mutability versus one-shot construction, mutation points, and projection boundaries are visible from names, types, and structure without requiring every line to be mentally executed. Memory ownership should be visibly under a Boundary/owner scope or an explicit higher-level owner, and State updates should not create pinball-like chains unless Flow, interaction groups, gates, or owner-side apply steps make the chain controllable and debuggable. If a reviewer cannot quickly tell what owns a value, what it is related to, whether it is meant to mutate, or when it changes, split the concept, rename it, or document the provisional risk before promoting the design.
- A good Loka abstraction should make application code feel simple without hiding where state lives or who cleans it up.
- Favor meaningful application code: app-facing APIs should express intent, ownership, and state flow rather than platform IDs, encoding buffers, or other incidental mechanics. Push platform-specific details down behind neutral names and thin value types when doing so keeps lifecycle and ownership understandable.
- Framework-facing names and contracts must not depend on vibes or leave room for competing interpretations. If users or maintainers could reasonably disagree about what an API means, tighten the name, split the concept, or make the ownership/lifecycle/dirty-flow contract explicit in the type shape before promoting it.
- Use `/** ... */` for class, struct, and API documentation comments that describe shipped concepts or contracts. Use `//` for local implementation notes.
- When an abstraction works, it should reduce future decisions, not create new special cases.
- Treat "magic" as acceptable only when the underlying structure remains inspectable and explainable.
- When a defensive comment is needed to explain how loose fields or a manual reset keep each other consistent, treat that as a refactoring signal: group the fields into a small type whose operations maintain the invariant structurally (see PHILOSOPHY "Structure Over Vigilance").
- Separate policy from mechanism inside framework internals: extract storage/chaining/cleanup mechanics into a small owning helper so the outer type reads as the intended sequence of decisions, and so resource release is guaranteed by the helper's destructor rather than by another loop running to completion.
- Judge internal extractions by what they delete. A good mechanism boundary removes redundant bookkeeping fields, per-item copies of aggregate data, and defensive comments; if wrapping only adds indirection and a name, the boundary is wrong or unnecessary.
- Treat writing a similar formula, loop, or sequence a second time as a stop-and-check signal. If two sites must agree to stay correct (reserve vs allocate, create vs destroy, attach vs detach, per-platform twins), give the shared fact one named home or keep the pair adjacent with an explicit cross-reference; deliberate platform-seam duplication should be marked so divergence is a choice, not an accident (see PHILOSOPHY "Structure Over Vigilance").
- For a fact some targets cannot answer, report presence and value from one query (`bool queryX(T &out)`), and let a target that cannot answer decline instead of substituting a value. Do not add an independent `hasX()` virtual beside it; if an availability or enumeration view is needed, implement it once in the base in terms of the queries so the two cannot drift (see PHILOSOPHY "Absent Is Not A Value").
- Give a family of such facts a generic surface only for enumerating and describing it; keep retrieval specific and typed. Do not introduce a variant return, a runtime type tag, or an enum-to-type map so that one getter can serve every member — the types differ because the uses differ, and no call site loops over them uniformly (see PHILOSOPHY "Describe Generically, Fetch Specifically").
- When switching over a closed enum, omit `default:` so an unhandled enumerator fails the build: `-Wswitch` is part of the `-Wall -Wextra` floor in `cmake/LokaWarnings.cmake`, and every preset that sets `LOKA_WARNINGS_AS_ERRORS` sets it `ON`. Add a trailing `_COUNT` enumerator when the set needs to be iterated, and require new members to be inserted before it.
- Do not hand-roll a class to get type safety a plain `enum` already provides. C++98 has no implicit conversion from an integral type to an enumeration, so a plain `enum` is already safe as a parameter type, while a class of static constants costs Classic binary size and gives up `switch` coverage checking (see PHILOSOPHY "Modern Type Safety Without Modern Assumptions").

## DSL And Composition

An application boundary composes once per mount.
Values that change reach nodes as State props registered by the receiving node
as its own dirty sources; `Stack(axisState)` and `Box().width(widthState)` are
the first two layout inputs migrated under this ruling.
Structure that changes is a seat: Match/Show switch arms; Keyed re-declares its
subtree when its key changes; no boundary recomposes.
A moving lazy window changes viewport State and replaces its LazyScope generation
when `(first, count, structureRevision)` changes. The kernel has no
recompose door; do not reintroduce one.
For declaration ownership and replacement sequencing, see
[Keyed declaration seats](docs/KeyedSeatDesign.md).

- For app-facing composition-form selection, Props/Definition conventions, and
  example style, follow [docs/API_STYLE.md](docs/API_STYLE.md).
- LazyView (#990) owns one window selection; only window items have component/native residents, with no per-item Show seats. LazyColumn/LazyRow are FixedGrid helpers, with a one-row margin by default. `LOKA_LAZYFLEX_MAX_ITEMS` stays a reserved-list-capacity admission contract, not a performance bound. [LazyView ownership and cost](docs/KeyedSeatDesign.md#from-agentsmd)
- Lazy-list items are Component Props: `T::NodeType` derives from `ComponentNodeWithProps<T>`. Content updates apply props only to the changed range intersecting the window; bindings follow props without re-declaration. Every successful window-key change replaces the generation and its item-local state, including overlap.
- Lazy-list focus v1: a window-key change destroys every item branch and loses focus; returning constructs fresh items without restoration. Native focus acceptance remains pending; Null retirement pins do not establish native keyboard-focus behavior.
- Loka compose should use DSL-style chaining; avoid local temporary variables when possible.
- Prefer `this->` for member access; keep it consistent across the codebase.
- Prefer `deferBind` for UI projection or lazy updates; use `bind` only when immediate recompute is required.
- RTTI (`dynamic_cast`) is prohibited in DSL/scene code due to severe performance impact on 68k. Use virtual methods (`asXxx()`) or `NodeKind` checks instead. Add new `asXxx()` methods to Node when type-specific access is needed.
- Attr policy (68k): keep default attr structs as small PODs (target roughly <= 16-32 bytes). Avoid embedding heavy owned data in default attrs; route heavier payloads through explicit extended/pro attr types or external state handles.

## Platform Rules
- UI layers should follow platform-native naming and conventions; core stays neutral.
- Classic Mac UI uses Toolbox/Control Manager APIs; avoid Carbon/Cocoa in Classic paths.
- Classic stability: avoid transient data in DSL props (e.g., pass stable pointers/references); if props own data, ensure copy/clone rebinds internal pointers safely.
- macOS support policy: library/core implementation targets Tiger through Snow Leopard compatibility; consumer applications are expected to run on Big Sur and newer and may integrate modern Swift/C++ features at the app layer.
- Consumer-application boundary: the rule above applies to applications built on top of Loka, not to this repository's library/core/example/platform code unless a repository-specific rule says otherwise.
- macOS architecture policy: default local debug/test builds in `CMakePresets.json` and `.vscode` should follow the host's native architecture (do not pin `CMAKE_OSX_ARCHITECTURES` for the default debug path). Cross-arch/universal release work should use the dedicated external scripts such as `ub2`, not the default VSCode debug tasks.
- macOS Objective-C policy: library/core code must stay ObjC1-style manual memory management (non-ARC); `@property`/`@synthesize` are allowed, but direct ivar access (`obj->ivar`) is forbidden in all library/core Objective-C(++) under `apple/macos/src` and internal state access must go through private getter/setter methods (examples may diverge only when explicitly documented). Only `assign` properties may be synthesized: a synthesized `retain` or `copy` setter calls `objc_setProperty`, which Tiger's Objective-C 1 runtime lacks, so those accessors are written by hand; `tools/ci/check_macos_objc1_runtime.py` refuses that and every other runtime name Tiger does not export (#1302).
- macOS examples policy: example targets default to non-ARC for consistency with library/core; ARC is allowed only as an explicit per-target opt-in when integration requirements demand it.
- Objective-C property policy (library/core): when using `@property`, always declare explicit ownership semantics (`retain`/`assign`/`copy`) and avoid implicit/default memory behavior.
- macOS support terminology: mark compatibility claims explicitly as either `build-verified` (compiles/links) or `runtime-verified` (launched/tested on target OS/hardware); do not mix these terms.
- Win32 wide-API policy: for any Win32 entry point that carries user-visible text or a file path, use the `W` (UTF-16) variant and build the logical `String` from the UTF-16 buffer (`CreateWin32StringFromUtf16`) — never from an `A` variant's bytes. [Win32 wide API history](docs/REVIEW_HISTORY.md#win32-wide-api) It applies to controls, common dialogs, window text and paths alike. Two exceptions: diagnostics (`OutputDebugStringA` and friends), which go `const char*` to the diagnostic seam by design and never reach an end user; and **documented test-only negative controls**, where a pin calls the `A` form deliberately to hold the loss mechanism in place so a regression fails instead of passing quietly (`tests/Win32EditTextBridgeTests.cpp` and `tests/Win32FilePathTests.cpp` both do this). A negative control must say in a comment why it is one.
- Win32 window-class corollary: register, create, and default windows with the matching `RegisterClassW`/`CreateWindowExW`/`DefWindowProcW` family even when the window name is empty. [Win32 wide API history](docs/REVIEW_HISTORY.md#win32-wide-api)
- Win32 path policy: never hand a path flattened to UTF-8 to a narrow CRT call (`fopen`, `_open`, `stat`); go through `loka::platform::file::OpenRead` or another seam that materializes the native path. The Toolbox preference for `fopen`/`fread` under Performance And Retro Targets is about Classic paths and does not license a narrow open on Win32.

## Performance And Retro Targets
- Cost lines are part of a door's definition (see Shape Review Gates): name the caller, frequency, and owner of the rows walked. [LazyView cost lines](docs/KeyedSeatDesign.md#from-agentsmd)
- Toolbox/68k binary size policy: avoid `std::fstream`/iostream-based file I/O in Classic paths because it pulls large libstdc++ locale/stream machinery; prefer C stdio (`fopen`/`fread`) or platform file APIs.
- Prefer intrusive linked lists over `std::vector` when elements are heap-allocated anyway; adding a `next_` pointer avoids separate allocations and reallocation costs. On 68k, this primitive approach often outperforms "smart" containers.
- Performance targeting policy: optimize primarily for 68030-era hardware and the repository's supported platform baselines; avoid regressions on low-end 68k (68000 / 68020) targets, but do not force 68k-first micro-optimizations without evidence.
- On 68k hot paths, avoid `StateStream` unless justified; manual `bind` + compute can be significantly faster for startup/compose.
- Performance triage steps: 1) reproduce on modern OS with profiling on, 2) capture tick breakdown, 3) isolate by commenting out components or toggling features, 4) optimize top hotspots first, 5) re-measure, 6) record findings in docs/TODO.md.
- For animated Classic UIs, prefer quantized output gating before expensive updates: if integer-position/rendered output is unchanged, skip rebuilding props/models and avoid `MutableState::set()`.
- On Toolbox hot paths, prefer simple `NodeContext`-local previous-state caching over pushing detailed dirty metadata through shared DSL/app models when the optimization is platform-specific.
- The dirty-rect heuristics from before the paint ledger (redraw triage order, redraw-area reduction, moving-rect erase) are superseded by context-owned damage with a counted fallback and kept only as [history](docs/REVIEW_HISTORY.md#classic-redraw-heuristics-pre-paint-ledger).

## Review Paths
- Every change is routed by the **surface it touches**, never by its line count or file extension. The author names the class in the PR body; a reviewer who disagrees moves it up, never down.
- Class E, editorial: prose, comments, formatting, or documentation that changes no requirement, no compatibility claim, and no example that is compiled or run. Required work: `git diff --check`, a one-line rationale, and the statement "no contract or compatibility claim changed". No candidate revision, no shape list, no bot round beyond the automatic one.
- Class C, contract or evidence: any text that states what the code guarantees, supports, or has verified — compatibility ranges, `build-verified` / `runtime-verified` claims, design rulings, rig protocols, this file, the delegation skill. Required work: cite the source of each changed claim (issue, commit, rig log) and state which existing evidence still applies and which is renewed; one independent read of the diff against those sources. Shape gates do not apply because no code shape changed.
- Class S, shape: anything that changes ownership, lifetime, dirty/layout/attach/detach routing, a public API meaning, a platform seam, or runtime behavior. Required work: the full sequence below — Gate 1 before the brief, complexity-flag profile, Gate 2 on the committed candidate, the codex-delegate pre-PR fixed point, and the verification policy for bug fixes and refactoring.
- Escalation triggers from E to C: the diff touches a sentence containing "supports", "verified", "requires", "must", "policy", or a version/OS/architecture name. From C to S: any hunk in an executable or configured surface — source under `common/`, `win32/`, `apple/`, `example/`, `tests/`, CMake files and presets, workflows, scripts, rig descriptors — or any test expectation change. Contract-only sources (this file, `DESIGN.md`, `PHILOSOPHY.md`, `docs/`, `plans/`, `.claude/skills/`, comments) stay in class C however far they are from `docs/`. Ambiguous cases take the higher class.
- Worked examples: a typo in the Programming Guide is E. #726's correction of two legacy "build-verified" paragraphs after SimpleViewer became a bundle is C (the claim changed, the binaries did not; the old evidence stays applicable to the old configuration and is said so). #709's transition-fact clearing is S.
- Evidence record, in the PR body: for class S, and for class C when it changes a compatibility or rig claim — candidate revision, base, configuration (preset, toolchain, OS, architecture, rig descriptor), `build-verified` or `runtime-verified`, result, and known limits. A class C change that alters only rulings or procedure records "evidence: non-runtime" plus the checks it ran (`git diff --check`, the assert audit, the independent read) and the sources cited. A later edit to the same PR states which entries remain valid without rebuilding and which were renewed.

## Shape Review Gates
- Two named passes look for structure that reads as bolted-on: one when a design is complete and before an implementation brief is written, one when an implementation is complete and before the PR is opened. Both produce a written list. Finding nothing is an allowed outcome; skipping the look is not, so the list must exist and say what was considered.
- Gate 1, design complete: (1) Does any new door, field, or piece of vocabulary repeat the shape of an existing one? Two parallel families with the same shape — a storage door per resident kind, a drain call per resident kind — mean the axis is wrong, and the existing one should carry the new case. (2) For each new wall, what happens when it is absent: undetected misuse, undefined behavior, or memory corruption? That consequence decides whether it is always-on, audit-build, or debug-assert. Copying the tier from a wall that merely looks similar is how this goes wrong. (3) Can the design be drawn with boxes and solid lines? A dotted line is a field its own type never reads, an identity kept only so someone else can compare it, or an object no scope owns. (4) Will the next resident of this kind need the same manual step? If yes, the step belongs inside the procedure, not at each call site. (5) Is any API shape chosen for test observability rather than for callers? (6) Does it add a primitive member — a `bool`, a counter, an index — to an existing type? A flag or counter loses the answer to "when was this set, and from where", the same loss the ownership rules exist to prevent, so it is refused unless it has exactly one writer, its owner is its only reader, and it cannot be derived from an existing phase, type, or return value. Derivable means do not add it: a tracker's re-entrancy depth was already its phase (#529). Two primitives carrying one meaning — a `bool` beside an index, a hand-rolled optional — become one small value type with an explicit none (`BranchArm`, #527). A mid-procedure result kept for a later reader travels as a return value, not a member (the sibling-tag collision set in #527). An owned `State` with a single write door, tracker registration, and explicit readers (`Window::nativeFrame()`, #525) is a box, not a flag, and is exempt. [Gate 1 worked incidents](docs/REVIEW_HISTORY.md#shape-review-gates--worked-incidents)
- Gate 2, implementation complete: (1) List every door, field, virtual, and call site the diff adds, and for each name the existing thing it parallels; every added primitive member (flag, counter, index) is named individually with its single writer, every reader outside the owning type (a foreign reader fails the gate 1 (6) shape even when the writer is unique), and the phase, type, or return value it could not be derived from. Every added door or call path also carries one cost line: who calls it, how many times per update cycle (per node? per retained node? per hit row?), and whose rows it walks. A door that walks rows owned by someone else — every ledger in a controller to find one context's entries, every hit to answer whether a State still has a user — is returned for reshaping, not noted as a medium smell: the rows belong with their owner, and a walk over foreign rows is the same misplaced-invariant shape as a foreign reader of a flag (#610's `refreshContextProps` walked seven ledgers on every retained props apply and was accepted from a smell list that had named it). [Gate 2 worked incident](docs/REVIEW_HISTORY.md#610--gate-2-check-1-foreign-ledger-walk) (2) If it added a step to a teardown or reclamation path, check every other path that reaches the same reclamation — one of them is usually missed. (3) If it added a check that disappears in some build configuration, state what happens in that configuration; a refusal that becomes memory corruption is not a diagnostic, it is a defect. (4) Do the PR body's claims match the tree — counts, test names, gating, evidence? (5) Record the findings in the PR body, including the ones deliberately left unfixed. (6) For deferred, queued, cached, or ledgered work, state one validity invariant, enumerate the concrete events that invalidate it, and pin them. Run the pre-PR review fixed point in the codex-delegate skill on the final committed diff; repeated findings on the same design or lifecycle axis return the change to design for splitting or reshaping rather than growing another case rule.
- Delegated implementation returns the same list. An agent that reports "no design forks encountered" without naming what it considered has not run the gate; require the candidates and their reasoning, ranked, even when the agent believes the work is clean.

## Debugging And Review
- When a test pins known-bad behavior, verify the loss or failure mechanism by instrumentation before writing the pin comment; do not infer it from code reading alone.
- For cross-layer behavior changes, combine both review modes deliberately: close reading of the diff and instrumented verification of the claimed mechanism. Each catches a class the other misses.
- When a correct fix would add another invisible coupling to a structure where multiple independent findings already point at the same missing concept, prefer parking the fix: keep the failure-mode tests as acceptance criteria, fix the structure first, then re-fix the bug deliberately on the new shape (PHILOSOPHY "Safe By Shape").
- For any PR touching lifetime, ownership, or allocation, run the five lifecycle review questions before deeper review: (1) Clock — does any release/drain happen outside a tick boundary, including re-entrant paths? (2) Ownership — is every new owning edge visible in a type, and is any new mini reference counter justified in the PR body (proliferating local refcounts signal a misplaced seam)? (3) Doors — does every logical-to-native crossing satisfy the ledger contract (registered by its owner, cancellable from detach, pinned by the clock while in flight, zero live entries at reclaim)? (4) Walls — is every invariant this change relies on pinned by an assert or test (if pinned, do not re-review the neighboring box's internals)? (5) Vocabulary — are retire/detach/reclaim used with their ruling meanings? A PR failing any question is returned for reshaping, not reviewed harder.
- Before opening, committing, or reviewing a non-trivial change, run a lightweight complexity gate. Count risk flags rather than trying to compute a perfect metric: new owner/lifecycle/cleanup paths; memory not clearly owned by a Boundary/owner scope or explicit higher-level owner; multiple new member fields or mutable flags; changes spanning two or more of State/Flow/Boundary/Platform; new cross-boundary state/callback/pointer sharing; raw callback/thunk lifetime that is not visible from the owner type; State update chains that can bounce between owners without a Flow/gate/interaction-group/owner-apply control point; dirty/layout/attach/detach/teardown behavior changes; ambiguous public API names; new fallback/default/implicit behavior; platform-specific workarounds leaking into common/app-facing code; or lifecycle/state-routing/layout/dirty behavior changes without tests.
- Complexity gate guideline: 0-1 flags is normal; 2-3 flags needs careful review and usually tests or explanatory comments; 4+ flags should be split or explicitly documented as provisional/follow-up work in a symptom-named GitHub issue or a narrow design note; 6+ flags should be rejected unless there is a strong design note and explicit owner approval. Unexplained complexity is a review failure even when the code works. Record the result in the PR body's `Review risk profile`: enumerate every triggered flag and the total (or explicitly say none), then map the flags to the review lenses and evidence they require. Forecast the profile at Gate 1 and reconcile it against the final diff at Gate 2. These flags route review; they are not a quality score, and this catalog remains their single named home.
- Hard stop unless explicitly justified: new `dangerously*` usage; cross-boundary mutable state sharing; Node/Boundary directly owning platform handles without a projection seam; raw callbacks/thunks stored across Boundary lifetimes; update-loop or lifecycle behavior changes without tests or TODO coverage; or a public API whose ownership/lifecycle meaning is ambiguous.
- Review lens for any diff touching `win32/`: scan the added lines for Win32 entry points ending in `A` (`...A(`, `OPENFILENAMEA`, `char buffer[MAX_PATH]`-shaped path handling). An `A` entry point on a text or path payload is a defect regardless of whether the current test data happens to be ASCII — the failure appears only with a full-width payload, and it appears far from the line that caused it.
- [Win32 wide API history](docs/REVIEW_HISTORY.md#win32-wide-api) **This wall does not retire the review lens.** Explicit `...A` calls still compile, and a text-bearing message payload stays invisible because `LPARAM` erases the pointer type — `SendMessage(hwnd, WM_SETTEXT, 0, reinterpret_cast<LPARAM>(bytes))` compiles under any setting. Those two shapes remain the reviewer's job permanently; the wall removes only the accidental unsuffixed case.
- The same lens must look past the added lines: when a diff gives an existing window new text or path traffic (`SetWindowTextW`, `SendMessageW(..., WM_SETTEXT, ...)`, `GetWindowText*`), check how that window's class was registered and created. [Win32 wide API history](docs/REVIEW_HISTORY.md#win32-wide-api) A new custom window class must pair its register/create/default family and extend the class-family contract test.
- If a crash occurs, first confirm whether it reproduces on a modern OS build; use breakpoints, LLDB commands, and targeted logging to identify the cause quickly.
- For runtime behavior regressions in compose/dirty routing, prefer path verification before speculative edits: place breakpoints on the user action handler, observed-state thunk(s), `Scene`/`PlatformController` apply path, and the target node's `composeWithContext`/`composeNode`, then confirm where the flow stops.
- A silent instrument is indistinguishable from a healthy system. Before concluding anything from a probe that never fires — a breakpoint not hit, a log line never printed, a watch never triggered — prove the probe *can* fire: give it a positive control, or verify its placement against reality (for a breakpoint, byte-compare the target memory with the image it was derived from). [398: silent instrument](docs/REVIEW_HISTORY.md#silent-instrument) Negative results carry evidence about the instrument first and the system second.
- A Classic application that returns to the Finder with no bomb and no dialog has usually aborted by contract, not "quit on its own": Retro68's `abort()` chain ends in `ExitToShell()`. An allocation failure is no longer silent: the Classic global `operator new` replacement (`apple/toolbox/src/ToolboxOperatorNew.cpp`) routes every plain-new/`std::vector` failure to `QuitForOutOfMemory` (`apple/toolbox/src/ToolboxOutOfMemory.cpp`), which shows the out-of-memory Stop alert before `ExitToShell()` whenever it can (#1107); the cases where it cannot are in that function. Only the `LokaNew`/`LokaAllocRaw` gate and nothrow `new` refuse with a null. [398: SIZE partition](docs/REVIEW_HISTORY.md#size-partition)
- If a request is ambiguous, stop and ask before implementing. In a delegated non-interactive run (`codex exec`), stop only for a question that changes ownership, lifetime, or a frozen ruling; for anything else, choose the option that mirrors the nearest existing shape, record the assumption in the PR body, and continue — a run that waits for an answer nobody can give delivers nothing.
- If a design or implementation path looks fragile, hard to reason about, or likely to cause intermittent bugs, prefer a small refactor toward a simpler structure first. If no clear low-risk refactor is apparent, stop and call it out to the user before building further on top of it.
- When an implementation reveals a gap in the framework itself — a step every rail or every next resident would have to repeat by hand, a fact the kernel cannot carry, a wall that can only be enforced by a friend list — do not work around it in the change at hand. Name the gap in the PR body, open a design rally page for it (one topic, one page, REFUTE before freeze), and sequence the follow-up before the next feature that would repeat the workaround. A framework pays the rework once at design time or once per rail forever; the #873 delivery-site enumeration (three rails hand-listing their completion tails, then a rail-wide ruling from a bot review) is the worked example.

## Verification Policy For Bug Fixes And Refactoring
- Bug fixes must demonstrate red->green: add or extend a test that fails (or hard-fails under ASan) on the pre-fix code, confirm that failure, then land the fix that turns it green. Record the pre-fix failure evidence in the PR.
- Refactoring must be behavior-preserving under pinned results: add characterization tests first where coverage is missing, then show identical results before and after the change in both the `testing` and `testing-asan` presets.
- Wiring and mechanism changes must be mutation-backed, not just suite-green: for each logical hunk that carries behavior (a new guard, a changed data source, a rewired lookup, a moved call), temporarily revert that hunk alone and confirm at least one test fails, then restore it. A hunk whose revert leaves the suite green is either untested (add the discriminating pin before merge, or record it as an explicit follow-up) or unnecessary (drop it for minimal diff). Note surviving mutations and their resolution in the PR.
- When the headless suite cannot discriminate a change (platform runtime behavior, menu/tick cadence, redraw semantics), verify on the affected OS: run the platform unit-test targets (`LokaTestsMacOS`, `LokaTestsWin32`) and/or drive the affected example flow on that platform.
- A check whose coverage depends on the host must name the condition that actually discriminates, and both branches must be run before the result is trusted. The machine you work on silently picks one branch, so the other is the one that rots, and a green exit code then covers a different amount on every machine. Two shapes of this landed a day apart: a rule that demanded ACP 932 when the pin it pointed at skips only on UTF-8 (`GetACP() != CP_UTF8`, `tests/Win32FilePathTests.cpp`), so it rejected valid evidence from every other non-UTF-8 code page and misread one rig's value as the criterion; and a launcher test that gated its PowerShell cases on "a PowerShell exists" when they need Windows PowerShell specifically — the Linux CI runners ship `pwsh`, entered the block, and went red on a `.cmd` stub. Where a branch is skipped, print it (`[skip] ...`) as the ACP pins already do; a silent skip is indistinguishable from coverage.
- For Classic targets, the machine verdict is the MAME scenario rail (`tests/toolbox/run-scenario.sh`, `LokaTest.cfg`, the golden bundle under `build/mame-scenario/golden`, `docs/LOKA_RIG.md`) for the cells whose golden identity is approved in the rig descriptor (`scripts/rig/toolbox/rigs/toolbox-maciix.ini`); a cell added after the last approval is staged and reviewed, not a verdict, until the bundle is re-baked and approved. A standalone Flow application (`LokaWindowClamp68K`-style, writing `LOG.TXT`) covers what a scenario cell cannot express; a change to Toolbox paint, layout, or control drawing also runs the PaintDamage standalone against its tracked log ([PaintDamage standalone](tests/toolbox/PaintDamageStandalone.md)). Real hardware (PowerBook 180c) is for observation, not verdicts (#422).
- If a discriminating test is impossible in the current fixture, state that explicitly in the PR and name the tracked follow-up issue or branch that will deliver it.

## Licensing
- Never commit an artifact whose license is not clear. Everything in the tree must be original to this repository or carry an explicit license that permits redistribution here; "probably fine" is not a license.
- Third-party content (sprites, images, fonts, sounds, sample data) may be fetched and used at development time, but pipelines that consume it must keep their outputs under `build/` (ignored) and must not offer a way to write into tracked paths. Original hand-authored assets are committable as themselves; the reproducible-from-an-in-repo-generator bar applies to pipeline outputs, not to source artwork.
- This covers indirect embedding too: a package, disk image, screenshot fixture, or test resource that *contains* unlicensed content is itself unlicensed content.
- When licensing is uncertain, stop and ask the human instead of committing.

## Build, Test, And Commit
- Retro68 workflow policy: if `.dsk` is mounted (emulator/host), unmount it before rebuild. Building while mounted can leave stale artifacts or produce corruption-like runtime issues; when users report corrupted/unchanged Classic output, first retry with `.dsk` unmounted, then rebuild.
- Parallel work policy: agents work in git worktrees owned by an **agent-side clone**, never by the human's clone. A branch checked out in a worktree cannot be checked out again in the repository that owns it, so a worktree created from the human's clone silently takes that branch away from them. Create it as `git -C <agent-clone> worktree add <path> -b <branch> origin/main`, on the WSL filesystem. Win32 golden and pre/post verification builds in the VM rig guest's own clone (win32-verify skill); the bare-metal flow that the same skill keeps for release evidence and explained version-to-version comparison still uses a worktree on an NTFS path under `/mnt/c`, because Windows tools cannot read the ext4 clone. Because the two clones are separate repositories, several agents can work in parallel and the human can still check out any branch, including the same one.
- Runtime-verification handoff: when a change reaches the point where only real hardware can discriminate it, stop at built-and-ready and hand over rather than asking the human to assemble the setup. Push the branch and state, in one place, the exact command to run and what a pass looks like. The human switches their own clone to that branch, builds and runs, and the agent keeps working on the next thing meanwhile.
- Handoff assets must travel with the branch: commit the fixture the repro needs, or commit the script that generates it, and name its path. A file left beside the binary in the agent's worktree does not reach the human — `build/` is ignored and the two clones are different directories, so pushing transfers only committed objects. Getting this wrong quietly restores the setup work the handoff exists to remove.
- Runtime evidence on the owning rig (Win32 VM, MAME, the macOS rigs) is part of a class S candidate and is produced by the agent; ask the human for a runtime check only when no rig covers the change, and then hand over built-and-ready as described above.
- Commit policy: Do not amend commits. Only small fixes found immediately after a commit may be amended.
- Build output policy: keep all generated build trees under `build/` using purpose/platform-specific subfolders (for example `build/Testing`, `build/macos/Debug`, `build/retro68/68k/Release`); do not introduce ad hoc top-level build directories such as `build-foo`.
- Test build output policy: use `build/Testing` as the canonical test build directory (`cmake -S . -B build/Testing -DTEST_BUILD=ON`, then build/ctest from there).
- When a directly runnable test environment is available (e.g. Linux/WSL headless), always build and run the relevant tests before committing code or test changes. Do not skip this step even for "obviously correct" changes.
- Test-only introspection/access APIs should not expand normal prod-facing surfaces; prefer isolating them under a dedicated `testing` namespace/access layer (or equivalent backdoor) rather than adding general-purpose getters for tests.
- Failure-injection convention: simulate OOM/clone failure through `TEST_BUILD`-only hooks in a `testing` namespace (fail-count style, e.g. `failMenuBarDefinitionClones(n)`), or through probe definitions with failing `clone()` overrides. Prefer fail-count hooks over one-shot hooks when the code under test retries within one flush, so the red stays deterministic.
- Failure-injection placement: implement `TEST_BUILD`-only hooks in a test translation unit (`tests/TestingHooks.cpp`, wired through `LOKA_SHARED_TEST_SOURCES`), never inside production translation units, for the same reason test-only access stays out of prod-facing surfaces (two bullets above). The unit-test executables that use `LOKA_SHARED_TEST_SOURCES` build that translation unit together with the common sources compiled under `TEST_BUILD` (on Linux through the `TEST_BUILD` configuration; `LokaTestsMacOS` and `LokaTestsWin32` compile the common sources into the executable since #117 and #118, 2026-07-18), so the production cores (`LokaWin32Core`, `LokaMacOSCore`) never carry a hook.
- When adding a new example target, add its run config to `.vscode/launch.json` and the matching build task to `.vscode/tasks.json` for its `preLaunchTask`.

### Compile-time contract pins
`tests/compile` is configured only when `TEST_BUILD` is set at configure time,
which today means the Linux `testing*` presets (the macOS and Win32 CI presets
define `TEST_BUILD` per target, not at configure, so they do not build the
pins). Register each pair with `loka_compile_pin(<name> REFUSES <tu> ACCEPTS <tu>)`.
The refusing TU must fail to compile; its accepting twin shares the same
includes and pins that the failure is the one expression, not a broken
environment, and it is part of ALL in every configuration that builds `tests/compile`.
Diagnostics are not matched because compiler wording differs; keep twins aligned
by hand (a typo confined to the refusing TU is not detected). `LOKA_COMPILE_PINS`
registers the refusal tests (ON in the `testing` and `testing-asan` presets);
the CTest build probes share one `RESOURCE_LOCK`. Building the accepting twins
on the macOS/Win32 toolchains is not wired; #172 closed on 2026-10-11 without it.
